# STALEM: краткий разбор проекта

## Задача

Игровые события происходят нерегулярно, относятся к разным региональным
серверам и важны пользователям именно в ограниченные временные окна. Ручная
проверка неудобна, поэтому STALEM собирает состояние сервиса, нормализует его и
доставляет персональные уведомления через Telegram.

## Что реализовано в закрытой production-версии

- поддержка регионов RU, EU, NA и SEA;
- мониторинг фактического начала и завершения событий;
- ориентировочный прогноз следующих событий;
- персональный сервер и часовой пояс пользователя;
- несколько типов настраиваемых уведомлений;
- история и статистика по каждому региону;
- отдельная личная статистика пользователя;
- отметка готовности к событию с защитой от повторного нажатия;
- текущая и лучшая серии подготовок, а также процент готовности;
- публикация прогнозов и активных событий через inline-режим Telegram;
- персональные ссылки и учёт новых пользователей по приглашениям;
- аналитика активности аудитории за разные периоды;
- fallback на последнее корректное состояние при сбое внешнего API;
- защита от повторной доставки одного уведомления;
- административные рассылки с предпросмотром и подтверждением;
- SQLite в режиме WAL, безопасные миграции и фоновые задачи;
- автоматические тесты миграций, временных зон, уведомлений, статистики,
  inline-сценариев и отказоустойчивости;
- GitHub Actions для проверки изменений перед слиянием;
- деплой на VPS через Git, read-only deploy key и systemd.

## Инженерные решения

Новые пользовательские функции не добавлялись в виде изолированных обработчиков
без общей модели данных. Для отметок готовности, inline-публикаций и приглашений
используются отдельные сущности и таблицы, а повторные действия блокируются на
уровне хранения данных. Это позволяет сохранять корректную статистику после
перезапуска сервиса и безопасно повторять фоновые операции.

Для публикации активного события STALEM сначала проверяет локальное состояние,
а при расхождении может дополнительно свериться с актуальным внешним источником.
Такой fallback снижает риск ложного отказа пользователю из-за временно
устаревшей локальной записи.

## Результат

Бот стал действующим сервисом для более чем 200 игроков. Проект прошёл путь от
одного пользовательского сценария до многорегионального приложения с
персональными настройками, наблюдаемостью, пользовательской аналитикой,
автоматическими проверками и безопасным процессом обновления production-сервера.

## Что демонстрирует публичный код

Публичная версия оставляет только общие инженерные решения:

1. порты и адаптеры вместо прямой зависимости бизнес-логики от API;
2. параллельный опрос регионов с изоляцией ошибок;
3. last-known-good fallback;
4. идемпотентную доставку уведомлений;
5. тестируемые in-memory реализации репозиториев.

Production-схема базы, inline-публикации, персональная аналитика, приглашения,
административные операции и реальная интеграция с API намеренно скрыты. Поэтому
showcase не содержит достаточных данных для запуска копии production-бота.
